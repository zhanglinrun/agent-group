# 写作风格指南

本指南定义技术报告的通用写作手法规则，适用于任何技术领域。

**核心立场**：技术报告的读者是**评审专家、甲方、决策者**——他们关心技术原理与效果，不关心你的代码叫什么名字。一切写法都从这个读者画像出发。

## 语言基调

**学术严谨 + 工程务实**。不是论文的晦涩，也不是 README 的随意，而是技术负责人向评审委员会汇报的口吻：有体系、有依据、有判断。

## 反 AI 化（最高优先级）

技术报告必须读起来像人写的，而非 AI 生成。以下是典型 AI 痕迹及其修正方法：

### 禁止过度使用解释性括号

AI 生成文本的头号特征是每个术语后面跟一个括号解释。技术报告的读者是专业人士，不需要每个词都括号注释。

| 错误写法（AI 味重） | 正确写法 |
|---------------------|---------|
| 采用门控循环单元（GRU）对序列进行时序编码（即逐步处理时间序列数据） | 采用 GRU 对序列进行时序编码 |
| 本系统通过钩子机制（Hook，一种在特定事件触发时执行回调的编程模式）实现... | 本系统通过事件钩子机制实现... |
| 该模块负责状态持久化（即将运行时数据保存至磁盘以便恢复） | 该模块负责将运行时状态持久化至本地存储，以支持跨会话恢复 |

**规则**：
- 术语首次出现时可以给**一次**全称+缩写，如"自动混合精度（AMP）"
- 之后一律用缩写，不再括号解释
- 禁止用"（即...）"、"（也就是说...）"、"（换句话说...）"做行内补充——如果需要解释，就用一个完整的句子说清楚

### 禁止有序列表代替段落

技术报告面向评审专家和甲方，不是开发文档。有序列表（1. 2. 3.）和无序列表（- - -）给人"PPT 提纲"或"README"的观感，缺乏论述深度。

| 错误写法（列表堆砌） | 正确写法（段落叙述） |
|---------------------|-------------------|
| 系统包含三个核心层：<br>1. PUA 话术层：...<br>2. 调试方法论层：...<br>3. 能动性鞭策层：... | 系统的设计围绕三个相互协作的能力层展开。话术层借鉴绩效管理文化构建压力旁白，通过角色绑定与绩效语境建立行为锚点。方法论层融合多种实战调试框架，为 Agent 提供结构化的问题解决路径。能动性层则通过主动出击机制将 Agent 从被动执行者转化为任务 Owner，杜绝"修完就停"的惰性模式。三者分别解决"不愿做"、"不会做"和"做不全"三类问题。 |

**规则**：
- 技术介绍部分**严禁**使用有序列表（1. 2. 3.）分点罗列
- 当需要表达并列概念时，用**段落内的自然语句衔接**，如"首先...其次...此外..."
- 仅在以下场景允许使用列表：参数配置表格、评估指标定义、数学公式的变量解释
- 衡量标准：如果一个列表可以改写为一段流畅的文字，就必须改写

### 减少冒号的使用

AI 生成文本另一个特征是冒号过多——"通过三重能力协同解决上述问题："、"现有方法主要包括以下三类："。这种写法让报告读起来像大纲而非论述。

| 错误写法 | 正确写法 |
|---------|---------|
| 系统通过以下机制实现状态恢复： | 系统的状态恢复依赖两项核心机制。其一是... |
| 现有方法的局限主要体现在以下三个方面： | 现有方法存在三方面的局限。在XX方面，... |
| 核心思路可概括为：... | 核心思路在于将...与...相结合，从而实现... |

**规则**：
- 冒号后面不接列表——如果要展开多个要点，用段落内的自然过渡
- 冒号仅用于公式引导（"损失函数定义为："）和直接引述场景
- 每段最多出现 1 个冒号

## 读者意识（面向评审专家/甲方）

技术报告的读者不了解你的代码仓库结构、文件命名、目录布局。他们关心的是**技术原理、设计思路、实现效果**。

### 禁止暴露代码实现细节

| 错误写法（暴露代码） | 正确写法（技术抽象） |
|---------------------|-------------------|
| 以 `failure-detector.sh` 为例，其工作流程为... | 以失败检测模块为例，其工作流程如下。系统从工具调用事件中... |
| 状态持久化涉及 5 类文件，存储在 `~/.pua/` 目录下 | 状态持久化涉及五类数据，由系统在本地存储中统一管理 |
| 配置文件 `config.json` 包含以下字段... | 系统配置包含以下核心参数... |
| 调用 `train.py --epochs 100 --lr 1e-3` 启动训练 | 训练阶段设置迭代轮数为 100，初始学习率为 0.001 |

**规则**：
- 禁止在报告正文中出现具体的文件名（`xxx.py`、`xxx.sh`、`xxx.json`）
- 禁止在报告正文中出现具体的目录路径（`~/.pua/`、`/src/models/`）
- 禁止在报告正文中出现命令行调用（`python train.py`）
- 用**功能性描述**替代文件引用：`failure-detector.sh` → "失败检测模块"，`config.json` → "系统配置"
- 用**参数说明**替代命令行：`--lr 1e-3` → "学习率设为 0.001"
- 若确实需要提及工程实现，放在"系统实现"章节中用概括性语言描述模块划分，而非逐文件列举

## 段落构建法

### 段落优先原则

技术报告的主体必须是**连贯的段落叙述**，而非列表、表格或提纲式罗列。每个技术概念应当用 3-5 句话的段落完整展开——说清楚是什么、为什么这样设计、怎么实现、效果如何。

段落不是越短越好。一个只有两句话的段落通常意味着展开不充分、技术介绍不到位。理想的技术段落长度为 4-8 句话，足以将一个概念讲透彻。

### "论点→展开→收束"三段式

每个段落遵循：首句亮出本段论点，中间 3-5 句用数据、公式或例子支撑，末句总结发现或衔接下文。

**范例 A**（图像分类）：
> 从消融实验来看，引入注意力模块后各类别的识别精度均有提升。Top-1 准确率从 76.3% 提升至 79.8%，涨幅 3.5 个百分点，其中长尾类别的召回率从 41.2% 提升至 52.7%，涨幅达 11.5 个百分点。这一差异在统计上具有显著性，且在三次独立运行中表现稳定。进一步分析表明，注意力机制使模型对稀疏类别的关键判别区域给予了更高权重，从而弥补了样本数量不足带来的特征学习缺陷。综合来看，注意力模块在特征聚焦方面对数据稀疏类别的增益尤为显著，是系统性能提升的主要贡献因素之一。

**范例 B**（推荐系统）：
> 在线 A/B 测试的结果验证了离线指标与线上行为之间的趋势一致性。实验组的点击率从 3.21% 提升至 3.67%，用户平均停留时长从 4.2 分钟增至 5.1 分钟，而次日留存率保持在 62% 左右无显著变化。值得注意的是，停留时长的增长主要集中在内容详情页而非列表页，说明推荐质量的提升确实引导了更深层次的内容消费。综合来看，新模型在提升短期互动指标的同时未损害长期留存，具备上线价值。

### 2. 章节间的逻辑衔接

每章开头的第一段必须完成两件事：
- **承上**：提到上一章做了什么（如 "在明确了数据集特性后..."）
- **启下**：说明本章要解决什么（如 "本章建立完整的理论框架"）

**范例**（通用导读句式）：
> 本报告将从以下四个方面对该系统进行详细阐述：首先介绍所使用的数据集的构成与统计特性；随后建立完整的理论框架与数学模型，涵盖数据表示设计、网络架构及损失函数构建；之后描述系统的工程实现细节与训练配置；最后通过定量指标评估与可视化分析，检验所提方法的性能。

此句式的核心模式为 **"首先...随后...之后...最后..."**，与具体领域无关。

### 3. 解释性段落的节奏

技术细节不能干巴巴地堆公式。遵循 **文字→公式→解释→意义** 的四拍节奏：

1. 用文字说明即将做什么（"编码器将输入序列映射为固定长度的隐状态向量"）
2. 给出数学公式
3. 逐个解释公式中的变量
4. 说明这个设计的意义或直觉（"该表征压缩了序列的时序依赖与语义信息"）

## 用词规范

### 精确描述而非模糊修饰

| 避免 | 替换为（示范模式） |
|------|--------|
| 效果很好/较好 | 准确率为 92.3% / BLEU 得分达到 34.7 |
| 有一定的提升 | 降幅约 23.6% / 提升 3.5 个百分点 |
| 大量数据 | 共 120,000 条训练样本 / 涵盖 50,000 张标注图像 |
| 显著优于 | F1 从 0.82 提升至 0.91（+0.09） |
| 某种程度上 | 具体说明什么程度、在哪个维度上 |

### 因果用词要审慎

- **可以说**："这一差异表明..."、"这与...设定一致"、"说明...起到了预期的作用"
- **要谨慎**："证明了..."、"由于..."（需要严格因果证据时才用）
- **关键原则**：对比实验 ≠ 消融实验，分组差异 ≠ 因果归因

**范例**（审慎归因）：
> 需要指出的是，该分组对比并不等同于严格的消融实验——两组在数据分布、样本难度等方面可能存在固有差异，因此不宜将性能差距完全归因于某单一模块的贡献。要严格评估该模块的增益，需要在相同数据上对比有无该模块的结果。

### 专有名词处理

- 首次出现时给全称+英文缩写："自动混合精度（AMP）"、"大型语言模型（LLM）"
- 后续直接用缩写
- 框架/工具名保留英文：PyTorch、TensorFlow、CUDA、Hugging Face

## 数据呈现原则

### 表格

- 每张表格必须有编号和标题："表X-Y [表格描述]"
- 表格紧跟其引用文字之后
- 表格后 1-2 句话点明关键发现
- 数值保留合理精度（根据领域惯例，如百分比到一位小数，绝对值到有效位数）

### 图表引用

- 格式："如图X-Y所示，..."、"如表X-Y所示，..."
- 图表说明（caption）要自含义：仅看图+caption 就能理解图意

### 对比数据

对比时必须给出三要素：
1. 两个比较对象的**具体数值**
2. **变化量**（绝对值或百分比）
3. 变化方向的**解读**

**范例 A**（检测任务）：
> 加入多尺度特征融合后，mAP@0.5 从 68.4% 提升至 74.1%，涨幅 5.7 个百分点，其中小目标（面积 <32×32）的 AP 提升最为显著，从 31.2% 升至 42.8%。

**范例 B**（NLP 任务）：
> 微调后的模型在 MMLU 基准上的平均得分从 61.3 提升至 68.9（+7.6），其中 STEM 类子集的增幅最大（+11.2），人文类最小（+3.8），表明微调数据的理工科偏向对不同领域的增益存在差异。

## 局限性写作

每篇报告的实验分析章节必须包含局限性讨论。三步写法：

1. **承认具体局限**（给数字）
2. **分析原因**
3. **指出改进方向**

**范例 A**（生成模型）：
> 在 FID 指标上，模型在 256×256 分辨率下得分为 12.3，但升至 512×512 后急剧恶化至 28.7。这表明当前架构的生成能力在高分辨率下显著退化，可能与上采样模块的感受野不足有关。后续可引入级联生成或扩散细化策略改善高分辨率质量。

**范例 B**（分类任务）：
> 模型在测试集上的整体 F1 为 0.91，但对 "其他" 类的召回率仅 0.47，意味着近半数边缘样本被误判。这主要源于训练数据中 "其他" 类的定义模糊且样本稀少。后续可通过扩充标注数据或引入对比学习改善该类别的区分能力。

## 排版细节

- 中文与英文/数字之间加半角空格："共 46 维"、"约 23.6%"
- 破折号用全角 "——"
- 列举用顿号 "、" 或分号 "；"
- 段落间空一行
- 标题与正文间空一行
