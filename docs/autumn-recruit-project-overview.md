# 秋招项目总览

## 项目定位

本项目定位为“学术 `Agent`（智能体）运行平台 + 额度交易一致性系统”。

用户先登录并购买额度，再使用额度运行学术 `Agent`（智能体）。系统需要保证订单、支付、拼团、退款和额度账本状态一致，同时让 `Agent`（智能体）只能读取后端事实，不能用模型回答直接决定余额、到账或退款状态。

## 用户主路径

1. 用户登录后进入工作台。
2. 用户通过直购或拼团购买额度。
3. 后端根据交易状态发放额度。
4. 用户运行学术 `Agent`（智能体），系统记录计划、工具调用、结果观察、产物和额度消耗。
5. 用户可查看运行回放、额度余额和额度流水；后台可核查交易记录和一致性结论。

## 两条主线

### 交易一致性

交易侧重点不是“能调支付接口”，而是保证状态和资金语义清楚：

- 直购支付成功后可以发放额度。
- 拼团支付成功只表示名额已支付，未成团不能发放额度。
- 拼团成团或交易完成后才能发放额度。
- 已到账订单退款后必须写额度回滚流水。
- 重复下单、重复回调、重复退款、重复补偿都要靠幂等键防止重复处理。

这一部分面试时重点讲“状态流水 + 补偿任务 + 幂等键 + 额度账本”。

### `Agent`（智能体）工程化

`Agent`（智能体）侧重点不是“接了大模型”，而是让用户对话运行可控、可回放、可评测：

- 固定执行链路：计划生成、工具调用、结果观察、产物保存、额度扣费、运行回放。
- `RAG`（检索增强生成）输出知识来源、召回片段和引用结果。
- 评测聚焦工具调用正确率、文件理解质量、回答一致性和额度扣减一致性。

这一部分面试时重点讲“模型负责用户对话、资料理解和内容生成，高风险交易事实来自后端系统”。

## 核心边界

- 余额只能由额度账本决定，不能由前端或模型决定。
- 支付成功不等于额度到账，拼团场景必须等成团。
- 支付宝沙箱只通过环境变量读取密钥，不把密钥写入仓库。
- 后台可以核查订单、支付、拼团、退款和额度流水；用户对话 `Agent`（智能体）不替代后台查账。
- 本轮不接微信支付沙箱，不拆微服务，不重写前端。

## 可展示证据

- 后端测试覆盖直购到账、拼团未成团不到账、退款额度回滚、重复回调幂等、金额不一致、沙箱配置检查。
- 支付网关状态接口展示沙箱模式、推荐渠道、缺失项、公网回调和渠道配置完整度。
- 后台交易核查输出订单事实、支付事实、拼团事实、退款事实、额度流水、异常标记和建议结论。
- 运行回放展示用户对话工具调用、产物和额度消耗；后台交易核查展示交易一致性结论。
- 工作台已经覆盖普通对话、`Skill`（技能）、图像生成、数据问答、`MRAG`（多模态检索增强生成）、交易看板、`MCP`（模型上下文协议）管理和 `Agent`（智能体）配置入口。缺少外部模型或外部生图服务时，系统会明确展示本地降级或未配置状态，不把外部依赖缺失伪装成生产能力。

## 三分钟讲述稿

这个项目是一个学术 `Agent`（智能体）平台，但我没有只做聊天功能，而是把它和会员额度、拼团交易、支付回调、退款回滚连在一起，重点解决“模型能力如何接入真实业务系统”的问题。

用户可以通过直购或拼团购买额度，再用额度运行学术 `Agent`（智能体）。交易系统负责订单、支付、拼团、退款和额度账本。`Agent`（智能体）负责用户对话、文件理解、知识库问答和产物生成，但它不能直接决定余额、支付状态或拼团状态，这些高风险事实都必须来自后端交易系统。

我在项目里重点做了两类工程化设计。第一类是交易一致性，直购支付成功可以到账，拼团支付成功但未成团不能到账，退款后要按到账流水回滚额度，重复回调和补偿任务通过幂等键避免重复处理。第二类是 `Agent`（智能体）可观测和可评测，运行过程会记录计划、工具调用、结果观察、产物和额度消耗，方便复盘用户对话质量和额度扣减是否一致。

所以这个项目的亮点不是技术栈多，而是把 `AI`（人工智能）应用放进一个有交易约束的真实业务场景里，并用测试、后台核查和运行回放证明关键状态是可信的。

## 简历亮点

- 设计并实现额度交易一致性链路，覆盖直购到账、拼团成团到账、未成团不到账、退款额度回滚和重复回调幂等处理。
- 构建学术 `Agent`（智能体）工具编排链路，支持计划生成、工具调用、结果观察、产物保存、额度扣费和运行回放。
- 建立交易一致性验证闭环，基于后端订单、支付、拼团、退款和额度流水核查关键状态，用测试报告验证核心场景。
