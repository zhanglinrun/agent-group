# 拼团式额度交易平台简历材料

## 项目描述

围绕 `Agent`（智能体）调用额度购买设计拼团式交易平台，支持直接购买、拼团活动试算、锁单参团、支付回调、成团结算、额度发放、退款回滚和交易排障。系统采用 DDD（领域驱动设计）分层，把活动、拼团、订单、支付、额度和补偿任务拆成清晰边界；直接购买在支付成功后发额，拼团购买必须等成团或交易完成后发额，避免“支付成功但未成团”导致额度提前到账。

## 核心技术

`Java 21`（后端语言）、`Spring Boot`（应用框架）、`MyBatis`（数据访问框架）、`MySQL`（关系型数据库）、`Redis`（缓存和分布式锁）、`RabbitMQ`（消息队列）、`XXL-JOB`（分布式任务调度平台）、`Docker`（容器化）、支付宝沙箱。

## 项目亮点

1. 交易状态一致性：通过订单流水、支付流水、额度流水和状态事件表记录关键流转；支付回调做验签、防重放和支付单幂等，拼团单只有在成团或交易完成后才触发额度到账。
2. 可靠事件投递：使用 `TradeEventOutbox`（本地事务消息表）保存交易事件，由 `RabbitMQ`（消息队列）异步投递；发送失败后按重试次数进入重试或死信状态，便于排障。
3. 企业化补偿调度：用 `XXL-JOB` 接管交易补偿任务，拆分为 Outbox 投递、业务通知重试、超时未成团退款、支付查单与未支付关单四类 handler；支持按 `orderId`、`uuid`、`teamId` 精准手动补偿。
4. 支付回调与业务通知分离：支付回调只表示支付网关通知本系统；成团或退款后的下游派发统一叫业务通知，支持 `MQ` 和 `HTTP` 两种方式，并通过补偿任务保证失败可重试。
5. 拼团履约边界清晰：直接购买支付成功即可发额，拼团购买支付成功只表示占位成功，必须等团队成团后发额；退款或误发场景通过额度流水回滚余额。

## 面试表达提醒

- 不写 `Kafka`（分布式消息系统），本项目实际使用 `RabbitMQ`。
- 不写 `Redis BitMap`（位图标签存储），当前项目没有补这条能力。
- 不包装“无锁化抢占”或“恢复量机制”，本项目重点是任务幂等、状态机和重复执行保护。
- 不把业务通知说成支付回调，支付回调只指支付宝/微信等支付网关调用本项目。
