# 灰度发布说明

本文只描述本项目可落地的灰度发布方式，用于演示和面试说明。

## 流量入口

`Nginx`（反向代理）统一承接前端静态页面和后端 `/api/` 请求。正式环境可以把后端拆成 `blue`（稳定版本）和 `green`（新版本）两个上游，再按请求头、用户尾号或比例切流。

## 建议策略

1. 先按用户尾号灰度：只让 `userId` 尾号命中的用户进入新版本。
2. 再按接口灰度：优先放开导购查询、知识检索这类只读接口，最后放开锁单、支付、退款。
3. 最后按比例灰度：从 5%、20%、50% 到 100%，每一步观察错误率、接口耗时、通知重试数和退款失败数。

## 回滚信号

- `/api/v1/gbm/trade/lock_market_pay_order` 错误率持续升高。
- `notify_task`（通知任务）出现大量 `RETRY`（重试）或 `ERROR`（失败）。
- `trade_event_outbox`（本地消息表）出现大量 `DEAD`（死信）。
- `SELF_CHECK`（自检）失败率升高，说明智能体回答缺少工具证据或检索证据。

## 数据库兼容

灰度期间只允许向前兼容的表结构变更：先加字段和新表，再发代码，最后清理旧字段。不能让新版本写入旧版本无法读取的核心交易状态。
