# 基础设施容器方案

## 一、为什么先补基础设施

导购接口不能长期依赖写死数据。第一阶段需要先把商品、知识片段、活动价格和后续交易状态落到本地数据源里，这样后面接 `RAG`、拼团、支付和评测时才能逐步替换实现，而不是每一步都改接口格式。

## 二、组件选择

| 组件 | 当前用途 | 后续用途 |
| --- | --- | --- |
| MySQL | 保存商品、活动和知识片段演示数据。 | 扩展订单、支付单、拼团队伍、退款单和评测记录。 |
| Redis | 先预留连接配置。 | 保存会话、缓存、限流和锁单状态。 |
| PostgreSQL + pgvector | 先建向量表。 | 保存知识片段向量，支持相似度检索。 |
| MinIO | 先创建对象存储桶。 | 保存上传的商品文档、营销文档、图片和解析结果。 |
| RabbitMQ | 先启动消息服务。 | 承接支付成功、成团成功、退款等异步事件。 |

## 三、当前落地范围

本阶段已经让导购流式接口通过 MyBatis 从 MySQL 读取：

- 商品基础信息。
- 拼团活动价格。
- 知识片段引用。

暂时不做：

- 真实向量召回。
- 真实文件上传解析。
- 真实支付回调。
- 真实消息消费。

## 四、启动方式

```bash
cd docs/dev-ops
docker compose -f docker-compose-environment.yml up -d
```

管理页面可选启动：

```bash
docker compose -f docker-compose-environment.yml --profile tools up -d
```

后端开发环境读取 `application-dev.yml` 中的本地容器配置。
