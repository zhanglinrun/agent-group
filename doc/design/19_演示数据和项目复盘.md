# 演示数据和项目复盘

## 一、目标

本阶段把项目整理成一条稳定演示链路，方便自测、答辩和后续继续扩展。

演示链路覆盖：

```text
导购提问 -> 知识检索 -> 流式回答 -> 商品卡片 -> 直接购买/拼团购买 -> 支付回调 -> 状态流水 -> 质量评测
```

## 二、演示数据

本地容器第一次启动时会执行：

```text
docs/dev-ops/mysql/sql/01-agent-group.sql
docs/dev-ops/mysql/sql/02-demo-data.sql
```

其中 `02-demo-data.sql`（演示数据脚本）补充了以下内容：

| 数据 | 内容 |
| --- | --- |
| 商品 | `G10001`（轻薄学习平板标准版）、`G10002`（高配创作平板）。 |
| 活动 | 标准版 3 人拼团价 2099 元，高配版 5 人拼团价 2899 元。 |
| 知识片段 | 商品详情、拼团规则、售后政策、评测样例。 |
| 交易样例 | 直接购买已支付订单、拼团已成团订单。 |
| 状态流水 | 下单、锁单、支付成功、成团结算等演示节点。 |

如果本地 `MySQL`（关系型数据库）容器已经初始化过，需要手动重新导入演示脚本：

```bash
docker exec -i agent-group-mysql mysql -uroot -pagent_group_dev agent_group < docs/dev-ops/mysql/sql/02-demo-data.sql
```

## 三、后端启动

先启动本地基础设施：

```bash
cd docs/dev-ops
docker compose -f docker-compose-environment.yml up -d
```

再启动后端：

```bash
cd backend
mvn -pl agent-group-app -am spring-boot:run -Dspring-boot.run.profiles=dev
```

后端默认端口为 `8080`（服务端口）。

## 四、前端演示入口

前端是静态页面，可以直接打开：

```text
frontend/index.html
frontend/admin.html
```

用户端重点演示：

- 输入“我是学生，预算有限，想买适合写论文和看网课的平板，哪款更合适？”
- 查看流式回答、知识依据、商品卡片、拼团价和购买入口。
- 上传图片后再次提问，验证图片线索会进入本轮导购。
- 连续追问“那拼团失败能退款吗”，验证多轮上下文。

运营端重点演示：

- 查看知识库、提示词版本、交易状态和评测面板。
- 点击“执行评测”，后端会运行 20 条典型导购用例。
- 评测指标包括检索命中率、回答准确率、推荐合理率和多轮一致性。

## 五、接口验收点

| 能力 | 接口 |
| --- | --- |
| 导购流式回答 | `POST /api/v1/agent/guide/stream`（导购流式接口） |

| 导购质量评测 | `POST /api/v1/evaluate/guide/run`（导购评测接口） |

## 七、项目复盘

本项目按“小版本、小能力、小提交”的方式推进，先固定接口契约，再逐步补齐领域模型、交易链路、知识库和评测闭环。

这套实现的重点不是一次性做全功能电商，而是验证一个电商导购系统从“信息搜索”走向“辅助决策”的工程闭环：

- 导购回答有知识片段依据，不只依赖静态文案。
- 商品推荐能落到结构化卡片、价格、拼团活动和订单状态。
- 交易链路有幂等、支付、成团、退款和状态流水。
- 评测结果能反向暴露检索、回答、推荐和多轮上下文的问题。

后续可以继续增强的方向：

- 接入真实大模型和向量数据库持久化检索结果。
- 将本地会话仓储替换为 `Redis`（缓存数据库）。
- 将上传文件保存到 `MinIO`（对象存储），并异步切片入库。
- 引入真实支付沙箱和消息队列，增强交易可靠性。
