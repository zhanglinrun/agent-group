# 秋招演示脚本

## 演示准备

- 后端服务已启动，数据库中有演示用户、商品、拼团活动和额度账户。
- 支付宝沙箱密钥只配置在本地环境变量或 `.env`（环境变量文件），不提交到 `Git`（版本控制工具）。
- 支付沙箱检查脚本已运行，并生成 `docs\dev-ops\reports`（沙箱检查报告目录）下的报告。
- 演示前先确认后端测试通过：`cd backend && mvn -pl agent-group-app -am test`（运行应用模块及依赖测试）。

## 链路一：直购支付成功后额度到账

目标：证明直购订单的支付状态和额度到账状态一致。

步骤：

1. 用户进入额度购买页，选择直购额度包。
2. 创建支付单并完成模拟支付或支付宝沙箱支付。
3. 查看订单状态变为 `PAY_SUCCESS`（支付成功）。
4. 查看额度账户余额增加，并生成 `ORDER_GRANT`（订单发放）流水。
5. 在后台核查订单、支付单和额度流水。

预期结果：

- 后台核查结论为 `QUOTA_GRANTED_CONSISTENT`（额度到账状态一致），或在补偿前短暂显示 `QUOTA_GRANT_REQUIRED`（需要发放额度）。
- 额度变化来自后端账本，不来自前端或模型回答。

## 链路二：拼团支付成功但未成团不发额度

目标：证明“支付成功”和“额度到账”被清晰区分。

步骤：

1. 用户发起拼团购买并完成支付。
2. 保持队伍未达到成团人数。
3. 查看订单状态为 `PAY_SUCCESS`（支付成功），拼团状态仍为处理中。
4. 查看额度账户没有新增 `ORDER_GRANT`（订单发放）流水。
5. 在后台核查订单、拼团队伍和额度流水。

预期结果：

- 后台核查结论为 `WAIT_GROUP_SETTLEMENT`（等待拼团成团）。
- 前端文案应显示“支付成功，等待成团”，不能显示“额度已到账”。

## 链路三：退款后额度回滚

目标：证明资金状态变化后，额度账本也能保持一致。

步骤：

1. 选择一笔已经到账的直购订单。
2. 发起退款或执行退款补偿。
3. 查看退款单状态和交易状态。
4. 查看额度账户写入 `REFUND_ROLLBACK`（退款回滚）流水。
5. 在后台核查退款单和额度回滚流水。

预期结果：

- 已到账订单退款后必须有回滚流水。
- 如果退款已发生但没有回滚流水，后台核查结论应提示 `REFUND_ROLLBACK_REQUIRED`（退款后需要回滚额度）。

## 链路四：支付宝沙箱回调

目标：证明官方支付沙箱不是只返回一个表单，而是能完成回调校验和状态推进。

步骤：

1. 运行支付沙箱检查脚本。
2. 确认 `officialSandboxReady`（官方沙箱就绪）为 `true`（真），`recommendedChannel`（推荐支付渠道）为 `ALIPAY`（支付宝渠道）。
3. 创建支付宝沙箱支付单，获取支付表单。
4. 在沙箱完成支付，等待异步回调。
5. 查看支付单状态、订单状态和额度到账状态。

预期结果：

- 回调验签通过后才能推进支付状态。
- 重复回调返回幂等结果，不重复发放额度。
- 金额不一致、订单不匹配、渠道交易号缺失时不能推进到账。

## 失败场景解释

- 支付宝沙箱未就绪：查看 `officialSandboxMissingItems`（官方沙箱缺失项），通常是密钥缺失或回调地址不是公网地址。
- 拼团支付成功但额度未到账：这是正确状态，因为拼团未成团不能发放额度。
- 退款后后台核查提示需要回滚：说明退款事实已经存在，但额度回滚流水缺失，需要补偿任务处理。
- `Agent`（智能体）回答和后端状态不一致：以后端交易事实为准，模型只能展示或解释事实，不能决定交易状态。
