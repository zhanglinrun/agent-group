# Tech Report — 项目→技术报告生成

将任意技术项目（ML/DL 模型、算法研究、系统工程、数据分析等）的代码、实验结果转化为一份逻辑严谨、公式完备、数据充实的中文技术报告（Markdown）。

## 触发后立即执行

1. **读取** `references/report-template.md` — 报告骨架与章节模板
2. **读取** `references/writing-style-guide.md` — 写作手法与语言规范
3. **读取** `references/formula-guide.md` — 数学公式排版规则

不读这三个文件就动笔 = 没有设计就写代码，产出必然不合格。

## 核心工作流

### Phase 1: 项目扫描（先搜后写）

深入理解项目再动笔。必须完成：

1. **代码结构扫描**：遍历项目目录，识别核心模块、模型定义、训练脚本、数据处理、评估脚本、配置文件
2. **模型架构提取**：从代码中提取网络结构（层类型、维度、激活函数、前向传播流程）
3. **数据流梳理**：数据格式 → 预处理 → 特征工程 → 模型输入 → 输出 → 后处理
4. **训练配置收集**：优化器、学习率、batch size、损失函数、早停策略、硬件环境
5. **实验结果汇总**：指标数值、对比表格、可视化图表路径
6. **数学符号统一**：从代码变量名映射到数学符号，全文一致

扫描结果暂存为内部笔记（不输出），作为后续写作的事实基础。

### Phase 2: 大纲设计

按 `references/report-template.md` 的章节模板，结合项目实际内容拟定大纲：

- 每个一级标题对应一个核心主题
- 每个二级标题对应一个独立逻辑单元
- 大纲中标注：此处需要公式 / 此处需要表格 / 此处需要图说明
- 大纲需要呈现给用户确认后再进入 Phase 3

### Phase 3: 逐章撰写

按大纲逐章展开，遵循以下约束：

**段落为王**（最高优先级）
- 技术介绍以连贯段落为主体，每个概念用 4-8 句话完整展开
- 禁止用有序列表/无序列表替代段落论述
- 并列概念用段落内自然过渡："首先...其次...此外..."
- 仅在参数配置表、指标定义、公式变量解释等场景允许使用列表/表格

**逻辑结构**
- 每章开头用 1-2 句话说明本章目标与上下文衔接
- 段落间有明确的逻辑递进（提出问题→分析原因→给出方案→验证效果）
- 每章结尾用小结段落收束

**反 AI 化**（详见 `references/writing-style-guide.md` 的"反 AI 化"章节）
- 术语只在首次出现时括号注释，后续直接使用
- 不用"（即...）"、"（也就是说...）"做行内补充
- 冒号后面不接列表，每段冒号不超过 1 个
- 不暴露代码文件名、目录路径、命令行——用功能性描述替代

**公式处理**（详见 `references/formula-guide.md`）
- 核心公式必须独立成行，使用 `$$..$$` 块级公式
- 公式前必须有文字引导（"可形式化为"、"定义为"、"计算如下"）
- 公式后必须有变量解释（"其中 $x$ 表示...，$y$ 表示..."）
- 行内引用变量使用 `$...$`

**表格处理**
- 参数配置、实验结果、数据统计等以 Markdown 表格呈现
- 表格必须有标题（如 "表3-1 关键参数配置"）
- 表格后需要 1-2 句话点明关键发现

**数据驱动**
- 所有定性结论必须有定量数据支撑
- 对比分析给出具体数值和百分比变化
- 局限性分析必须诚实指出不足

### Phase 4: 质量审查

完稿后自查：

- [ ] 章节编号连续且层次正确
- [ ] 所有公式变量在首次出现时有定义
- [ ] 符号全文一致（不出现同一概念用不同符号）
- [ ] 每张表格有标题和解读
- [ ] 结论段有数据支撑，无空口断言
- [ ] Markdown 语法正确，公式可渲染
- [ ] 全文无有序列表用于技术介绍（参数表/指标定义除外）
- [ ] 全文无代码文件名、目录路径、命令行出现
- [ ] 括号注释未过度使用（术语仅首次括号注释）
- [ ] 每段冒号不超过 1 个
- [ ] 每个技术概念有 4 句以上的段落展开

## 输出规范

- 格式：单个 Markdown 文件
- 语言：中文（专有名词保留英文原文，如 GRU、AMP、PyTorch）
- 公式：LaTeX 语法，`$$` 块级 + `$` 行内
- 图表引用：使用 "如图X-Y所示"、"如表X-Y所示" 格式
- 章节编号：阿拉伯数字层级制（1. / 1.1 / 1.1.1）

## 禁止行为

**事实层**
- 禁止未扫描代码就编造技术细节
- 禁止定性断言无数据支撑（"效果很好" → 必须有指标）
- 禁止符号冲突（同一符号不同含义，或同一概念不同符号）
- 禁止跳过大纲确认直接成稿

**公式层**
- 禁止公式孤立出现（无引导、无解释）

**反 AI 化（与事实层同等优先级）**
- 禁止过度使用解释性括号——术语首次出现可括号注释一次，后续禁止。禁止"（即...）"、"（也就是说...）"式的行内补充
- 禁止用有序列表（1. 2. 3.）或无序列表（- - -）替代段落叙述——技术介绍必须用连贯段落展开，而非列表罗列
- 禁止冒号后接列表的写法——"本系统包含以下三个模块：" 后面跟 1. 2. 3. 是典型 AI 输出模式，改为段落叙述
- 每段冒号不超过 1 个

**读者意识**
- 禁止在正文中出现具体的代码文件名（`xxx.py`、`xxx.sh`）、目录路径（`~/.xxx/`）、命令行调用（`python xxx.py`）
- 读者是评审专家/甲方，不了解代码仓库——用功能性描述替代文件引用（"失败检测模块"而非"`failure-detector.sh`"）

**内容充实度**
- 每个技术概念至少用 4-8 句话的段落完整展开，2 句话的段落意味着展开不充分
- 禁止用浅层描述敷衍——必须说清楚是什么、为什么这样设计、怎么实现、效果如何
