## 🔧 如何获取交易链路真实性能数据

### 压测前准备

1. **启动依赖环境**：
   ```bash
   cd docs/dev-ops
   docker compose -f docker-compose-environment.yml up -d
   ```

2. **启动后端服务**：
   ```bash
   cd backend
   set SPRING_PROFILES_ACTIVE=dev  # Windows
   mvn -pl agent-group-app -am spring-boot:run
   ```

3. **准备测试数据**：确保数据库有可用的额度包和拼团活动（可用 `docs/dev-ops/mysql/sql` 初始化数据）

4. **获取登录令牌**：调用 `POST /api/v1/auth/login`

### 运行压测

```bash
cd docs/dev-ops/loadtest

# 压测拼团锁单（推荐先跑这个）
jmeter -n -t trade-loadtest.jmx \
  -JHOST=localhost -JPORT=8080 \
  -JTOKEN=你的登录令牌 \
  -JGOODS_ID=G10001 -JACTIVITY_ID=A10001 \
  -JTHREADS=50 -JRAMP=10 -JDURATION=60 \
  -l group-buy-result.jtl -e -o group-buy-report
```

压测结果在 `group-buy-report/index.html`，重点看：
- **Throughput（吞吐量）** → 这就是 QPS
- **90th/95th/99th pct（百分位响应时间）** → P90/P95/P99
- **Error %（错误率）**

### 建议的优化路径

按这个顺序做，能得到完整的"优化故事"：

1. **基线测试**：默认配置跑一轮，记录 QPS 和 P99
2. **定位瓶颈**：观察数据库连接池、Redis、分布式锁等待时间
3. **逐项优化**：
   - 调整数据库连接池大小（`HikariCP maxPoolSize`）
   - 优化 Redis 连接配置
   - 缓存活动信息减少数据库查询
   - 放宽锁粒度（如果安全）
4. **记录结果**：每轮优化后重新压测，记录到 `loadtest/README.md` 的结果表

### 面试时怎么讲这组数据

**结构**（2 分钟）：
1. **背景**：拼团锁单涉及分布式锁、幂等校验、库存扣减，是典型的高并发场景
2. **基线**：初始 QPS 约 X，P99 约 Y ms
3. **瓶颈**：通过监控发现瓶颈在【数据库连接/Redis/锁等待】
4. **优化**：【具体做了什么】，QPS 提升到 X，P99 降到 Y ms
5. **权衡**：【这个优化牺牲了什么/为什么这样做】

**示例话术**：
> "拼团锁单是典型的高并发场景，涉及分布式锁、幂等检查、原子扣减。我做压测时发现初始 QPS 只有 300，P99 响应时间 500ms，瓶颈在数据库连接池。我把 HikariCP 的 maxPoolSize 从 10 调到 20，同时给活动信息加了本地缓存，QPS 提升到 600，P99 降到 150ms。这个优化的权衡是：缓存带来了一致性窗口期（活动信息变更后最多 30 秒生效），但活动配置很少变，可以接受。"
