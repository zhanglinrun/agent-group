# 项目复盘：电商可信导购 Agent

## 一句话定位

我做的不是普通电商增删改查，也不是单纯聊天机器人，而是把导购 `Agent`（智能体）、拼团营销和支付交易串起来：模型只负责理解意图、规划工具和组织回答，价格、拼团、订单、支付、退款这些高风险信息都必须由后端交易工具和知识库提供；导购推荐进入下单前还会生成 `decisionId`（决策编号），下单时重新校验商品、活动和报价。

## 为什么这样设计

普通 `RAG`（检索增强生成）导购容易停留在“检索几段文档再回答”，面试时会被认为像演示项目。这个项目的主线是“导购决策进入拼团交易和支付闭环”，核心难点变成三件事：

1. 大模型不能编造价格、库存和订单状态。
2. 拼团、支付、退款这些状态要能幂等处理和补偿。
3. 回答质量要能被评测和监控，而不是只靠人工感觉。

## 我重点解决的问题

1. 工具治理：把知识检索、商品推荐、拼团试算、订单查询封装成后端工具，并为每个工具维护版本、风险等级、重试次数、结果引用要求和执行审计，模型只能选择白名单工具，不能直接访问任意接口。
2. 流式可解释：前端实时展示工具计划、工具调用、检索依据、商品卡片、拼团试算和回答内容，让用户知道系统查了什么。
3. 决策快照：每次导购推荐会记录商品、活动、报价、知识片段、工具调用和报价过期时间；直接购买和拼团锁单都必须携带决策编号，后端重新校验金额一致性。
4. 拼团交易闭环：从导购推荐进入拼团购买后，后端完成营销锁单、库存占用、团队名额、支付成功后的成团结算、未成团退款和通知任务。
5. 支付一致性：支付单创建、支付回调、防重放、超时关单、退款补偿都围绕订单状态流转设计，避免重复扣款、重复占名额和状态不一致。
6. 知识库治理：上传文档后进入对象存储、文本解析、知识切片、`Spring AI VectorStore`（向量存储接口）检索链路；查询时融合向量召回和关键词召回，再按业务关键词重排，保证商品编号、拼团、退款、售后这类事实优先命中。
7. 质量评测：50 条评测用例检查检索命中、回答准确、推荐合理、多轮一致、工具调用、工具参数、工具结果引用和交易金额一致性，并设置回归门禁。
8. 可观测性：接入工具调用次数、工具耗时、模型耗时、向量检索回退、交易补偿等指标，能解释慢在哪里、错在哪里。

## 面试讲法

如果面试官问“这个项目和培训班项目有什么区别”，可以这样回答：

“我没有只做一个聊天页面，而是把导购 `Agent`（智能体）接到了拼团和支付交易系统里。比如用户问拼团价，模型不能直接回答，必须先规划 `group_trial`（拼团试算）工具，再由后端根据真实商品编号查活动服务；推荐结果会生成 `decisionId`（决策编号），用户点击拼团购买时后端还会校验商品、活动、报价和过期时间，然后才进入营销锁单、库存占用、支付单创建、支付回调和成团结算链路。订单和退款状态同理，只能走后端工具，避免模型幻觉。”

如果面试官问“怎么证明效果”，可以回答：

“我做了离线评测集，覆盖商品推荐、拼团报价、售后规则、订单查询和多轮追问。每批评测会产出检索命中率、回答准确率、推荐合理率、工具调用正确率、工具参数正确率和工具结果引用率，并设置工具调用正确率、工具结果引用率、回答准确率的回归门禁。不是只看一次演示，而是能持续对比版本效果。”

如果面试官问“工程上有哪些兜底”，可以回答：

“知识向量库不可用时有本地检索兜底，大模型接口不可用时有基于商品资料和知识片段的兜底回答；支付回调有防重放，拼团锁单有幂等键，交易事件用 `Outbox`（事务消息表）和补偿任务降低状态不一致风险。”
