# 交易链路高并发设计说明

这份文档把交易系统里和并发、一致性相关的设计整理成"问题—方案—权衡"的形式，主要给两类场景用：一是面试时讲清楚每个设计为什么这么做，二是后续改造时先看这里再动手。涉及的类名只在需要定位代码时出现，描述以业务语义为主。

## 一、拼团下单：怎么防超卖和重复下单

**问题**：同一个用户连点两次、同一个队伍多人同时抢最后一个名额、活动库存被并发扣穿，这三件事都发生在锁单这一个入口上。

**方案**：分三层处理。

1. 入口防重：锁单接口加 `DistributedLock`（基于 Redis 的分布式锁），锁的粒度是"用户 + 活动 + 幂等键"，同一个请求的重复提交在入口就被串行化。
2. 业务幂等：每个锁单请求必须带 `idempotentKey`（幂等键）。已存在的幂等键直接返回原来的订单（标记 `repeated`），同一个幂等键换了商品或活动则报错拒绝，防止前端重试把参数带错。
3. 名额控制：活动库存和队伍名额在数据库层做原子扣减，锁新队伍和加入已有队伍走不同分支；加入失败时回补队伍名额，避免名额被失败请求占住。数据库之前还有一层 Redis 有界计数做预检（自增超过可加入名额即回退拒绝，按订单号幂等释放），它只负责在高并发下把明显超额的请求挡在数据库之前，Redis 异常时直接放行，名额正确性始终以数据库为准。

**权衡**：分布式锁只锁"同一个请求"而不是整个活动，吞吐量不受单个热点活动拖累；真正的名额正确性交给数据库原子操作兜底。代价是失败路径要自己负责回补名额，这部分逻辑比"一把大锁"复杂。

## 二、支付回调：怎么做到重复回调不重复处理

**问题**：支付网关的回调可能重复发、乱序发、并发发，回调处理又涉及订单状态、拼团结算、额度发放一长串动作。

**方案**：四道闸门依次过。

1. 验签：回调先验签名，不通过直接拒绝。
2. 已完成检查：查这笔回调是否已经处理完成，是就直接返回上次的结果。
3. 处理中互斥：`PaymentWebhookReplayGuard`（回调防重放守卫）用 Redis 锁保证同一笔回调同时只有一个实例在处理，拿不到锁的返回"处理中"让网关稍后重试；只有在没有 Redis 仓储的环境（主要是单测）才退化成单机内存模式，并打告警日志。
4. 状态幂等：进了处理逻辑后再看支付单状态，已经是支付成功的只做补偿性的额度核对，不重复走状态流转。

**权衡**：处理中冲突选择"快速失败让网关重试"而不是排队等待，实现简单且不会把回调线程占满；代价是依赖网关的重试机制，这正好是支付网关本来就承诺的行为。

## 三、额度发放：怎么保证"该发的只发一次，不该发的发不出"

**问题**：额度是这套系统里的"钱"。重复回调、补偿任务、管理端补发可能并发触发同一笔订单的发放；拼团订单还有"支付成功但未成团"这个不能发的窗口期。

**方案**：

1. 状态门槛：发放前先校验订单状态——直接购买要求 `PAY_SUCCESS`（支付成功），拼团购买要求 `GROUP_SETTLED`（拼团已成团）或 `DEAL_DONE`（交易完成），不满足直接返回，前端和 Agent 都没有能力绕过。
2. 流水幂等闸门：发放前先写一条发放流水，`user_quota_flow` 表上有 `uk_user_biz_flow`（用户 + 流水类型 + 业务单号）唯一约束。并发场景下只有一个事务能写入成功，撞唯一键的事务把结果当作"已发放"返回，余额加值只在流水写入成功后执行。
3. 完成态推进：发放完成后把订单推进到 `DEAL_DONE`，让后续补偿任务能识别"这单已经处理完"。

**权衡**：流水先行意味着流水里记录的"变动前后余额"在极端并发下是计算值而不是实测值，牺牲了流水字段的精确性，换来发放动作本身的强幂等。余额的真实性始终以账户表的原子加减为准。

## 四、成团结算：怎么把"最后一个支付的人"变成全队发放

**问题**：成团是由最后一笔支付触发的，但发放对象是全队所有人；结算和发放如果掺在一起，部分失败时很难恢复。

**方案**：结算规则链分两步——先原子地把这笔订单的名额标记为已支付（重复结算在这里被幂等挡掉），队伍达到目标人数后，把同队所有已支付订单批量推进到 `GROUP_SETTLED`，再按订单号逐一走上面第三节的发放流程。发放对每个订单独立幂等，部分失败可以靠补偿任务重放。

**权衡**：结算和发放拆开后多了一个中间状态（已成团未发放），需要补偿任务覆盖；换来的是每一步都可以安全重试，不存在"半成团"的脏状态。

## 五、可靠性：本地消息表和定时补偿

**问题**：结算通知、退款通知要发到消息队列；消息队列不可用时主流程不能跟着失败。

**方案**：交易事件先落 `TradeEventOutbox`（本地消息表），和业务在同一个事务里提交；投递任务异步把事件发到 RabbitMQ，失败重试、超限进死信。另有三类定时补偿：关闭超时未支付订单（先向网关对账再关单）、超时未成团退款、通知任务重试。所有定时任务通过 `ScheduledJobLockExecutor`（任务级分布式锁）保证多实例只跑一份。

**权衡**：本地消息表带来一张表的写放大和一个轮询任务，换来"业务成功则事件必达"的保证；事件投递是至少一次语义，消费端要自己幂等。

## 六、退款：怎么把钱、额度、会员、名额一起退干净

**问题**：退款不只是调支付网关，还要回滚已发放的额度、撤销已开通的会员、释放拼团名额，每一步都可能被重复触发。

**方案**：

1. 退款单幂等：同一订单的重复退款请求直接返回已有退款单。
2. 额度回滚：按当初的发放流水原额回滚，写 `REFUND_ROLLBACK`（退款回滚）流水，同样受唯一约束保护；允许余额变负，保证账实相符。
3. 会员撤销：会员套餐订单退款时，撤销该订单对应的一个会员周期——续费单回退一个月有效期，新开通的直接到期，并写一条 0 额度的回滚流水做幂等标记。
4. 名额释放：拼团订单退款后释放队伍名额，并创建退款通知任务。

**权衡**：会员撤销采用"按周期回退"而不是按天折算退费，规则简单、可解释，和"按订单整笔退款"的支付侧行为对齐；如果以后要支持按比例退费，需要把扣费记录细化到天。

## 七、面试时可以主动讲的边界

- 项目里有两类容易混淆的"通知"，方向相反：支付回调是网关调我们（带验签和防重放，见第二节）；成团/退款通知是我们告诉下游"业务结果出来了"（默认投 MQ 队列，可配 HTTP 推送，失败靠定时任务重试）。被问"这算什么回调"时，先把方向讲清楚。
- 拼团校验（活动可用性、参与上限、决策快照、名额预占）就是一段固定顺序的检查，用普通方法顺序调用实现，没有引入规则链框架——顺序逻辑不需要框架，这本身就是一个可以讲的取舍。
- 流水里的前后余额在并发下是计算值（见第三节权衡），被问到"流水余额准不准"时直接讲这个取舍。
- 事件投递是至少一次，消费端幂等是约定而不是框架强制。
- 回调防重放在没有 Redis 的环境退化为单机模式，多实例部署必须配置 Redis 仓储，退化时有告警日志。
- 性能数字一律以 `docs/dev-ops/loadtest` 的实测记录为准，不引用没有出处的数字。
