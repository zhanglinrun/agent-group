# 秋招演示脚本

## 演示准备

- 后端服务已启动，数据库中有演示用户、商品、拼团活动和额度账户。
- 支付宝沙箱密钥只配置在本地环境变量或 `.env`（环境变量文件），不提交到 `Git`（版本控制工具）。
- 演示前运行 `.\docs\dev-ops\scripts\payment-sandbox-check.ps1 -RequireOfficialSandbox`（严格沙箱检查），确认 `officialSandboxReady`（官方沙箱就绪）为 `true`（真）。
- 后端测试通过：`cd backend && mvn -pl agent-group-app -am test`（运行应用模块及依赖测试）。

## 链路一：直购支付成功后额度到账

1. 用户进入额度购买页，选择直购额度包。
2. 创建 `ALIPAY`（支付宝沙箱）支付单，完成沙箱支付。
3. 支付宝异步回调通过验签后，订单进入 `PAY_SUCCESS`（支付成功）。
4. 后端发放额度并写入 `ORDER_GRANT`（订单发放）流水。
5. 后台交易核查返回 `QUOTA_GRANTED_CONSISTENT`（额度到账一致），或在补偿前短暂返回 `QUOTA_GRANT_REQUIRED`（需要发放额度）。

## 链路二：拼团支付成功但未成团不到账

1. 用户发起拼团购买并完成支付宝沙箱支付。
2. 队伍未达到成团人数。
3. 订单保持 `PAY_SUCCESS`（支付成功），前端显示“支付成功，等待成团”。
4. 额度账户没有新增 `ORDER_GRANT`（订单发放）流水。
5. 后台交易核查返回 `WAIT_GROUP_SETTLEMENT`（等待拼团成团）。

## 链路三：拼团成团后额度到账

1. 同队用户完成支付，使队伍达到成团人数。
2. 拼团结算规则链把同队订单更新为 `GROUP_SETTLED`（拼团已成团）。
3. 后端按成团结果发放额度。
4. 后台交易核查返回 `QUOTA_GRANTED_CONSISTENT`（额度到账一致）。

## 链路四：退款后额度回滚

1. 选择一笔已经到账的订单发起支付宝沙箱退款。
2. 退款成功后写入退款记录。
3. 后端写入 `REFUND_ROLLBACK`（退款回滚）额度流水。
4. 如果退款已发生但缺少回滚流水，后台交易核查返回 `REFUND_ROLLBACK_REQUIRED`（退款后需要回滚额度）。

## 链路五：学术 `Agent`（智能体）扣减额度并回放

1. 用户发起学术问答、文件问答或资料整理任务。
2. 额度不足时任务被拒绝，不调用模型。
3. 任务成功后写入运行账本、模型调用、工具调用、产物和额度消耗流水。
4. 回放页展示用户问题、计划、工具调用、产物、额度消耗和最终回答。

## 失败场景解释

- 支付宝沙箱未就绪：查看 `officialSandboxMissingItems`（官方沙箱缺失项），通常是密钥缺失或回调地址不是公网地址。
- 重复回调：返回幂等结果，不重复发放额度。
- 金额不一致、订单号不匹配、渠道交易号缺失或验签失败：不推进本地支付状态。
- `Agent`（智能体）回答和后端状态不一致：以后端交易事实为准，模型只能解释事实，不能决定余额、到账、退款或拼团状态。
